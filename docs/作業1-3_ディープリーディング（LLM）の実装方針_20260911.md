## 1. 作業1: 事実確認（コードレベル）

### 1.1 「ディープリーディング」は文言だけで、機能の実体が無い

```dart
// mobile_app/lib/features/reading_result/presentation/reading_result_screen.dart:302-306
OutlinedButton(
  onPressed: () => Navigator.of(context).pushNamed('/paywall'),
  child: Text(l10n.deepReading),
),
```

実装の全量がこれである。`grep -rn "deepReading|deep_reading|ディープリーディング"` の結果は
**この1箇所と l10n の3言語ぶんのみ**で、バックエンド・API・モデル・課金のいずれにも存在しない。

### 1.2 LLM 連携の基盤は一切無い

`grep -rn "openai|anthropic|llm|gpt|claude" src/ scripts/` は **0件**。
外部サービス連携の前例は次の2つで、どちらも同じ形をしている。

| 連携 | 設定 | サービス | 既定 |
|---|---|---|---|
| レシート検証 | `ReceiptVerificationConfig`（`mode` + 環境変数） | `receipt_verification.py` | `local` |
| プッシュ配信 | `PushDeliveryConfig`（`mode` + 環境変数） | `push_sender.py`（`Protocol` + `Noop…` + `FcmV1…`） | `noop` |

`orchestrator.py` の `_build_receipt_verifier` / `_build_push_sender` が
`runtime_mode`（local/staging/production）を見て、**本番で擬似モードなら警告または起動拒否**する。
∴ **新しい外部連携の作り方は既に確立している。発明せずこれに合わせる。**

### 1.3 禁止表現の検査材料はマスタに既にある

```json
{"name": "励ましトーン", "endings": ["〜できます", …], "avoid": ["〜できません", "〜無理です", "〜諦めましょう"]}
```

`感情トーン設定` の `avoid`（避けるべき表現）が `card_content.json` の `tones` に取り込まれている。
承認方針 §7.3-2 が求める「機械的な検査」の材料は**新規に用意する必要が無い**。

### 1.4 課金・権限の規則はマスタが持っている

第1段で `スプレッド定義` シートへ `required_tickets` / `allowed_plans` を追い出し、
`BillingService.can_use_spread` / `required_tickets_for` / `consume_for_spread` が
**定義を受け取って判定する**形になっている。ディープリーディングも同じ枠に載せられる。

### 1.5 同意を取る仕組みが無い

`User` は `plan` / `tickets` / `subscription_expires_at` / `visit_count` のみで、
**同意の記録先が無い**。オンボーディング画面は2026-09-09に起動導線から外してある。

## 3. 作業3: 修正方針

### 3.1 何をする機能なのか（定義）

**既に出ている結果を、相談内容に寄せて推敲し直す有料オプション。**
占い直しではない。カードも引き直さない。

- 入力: 内蔵エンジンが作った本文＋相談内容＋カード／ポジション／テーマの素材
- 出力: 推敲後の本文（日本語のみ。組み合わせ解釈と同じ扱い）
- 失敗時: **内蔵エンジンの本文のまま返す**。チケットは消費しない

### 3.2 責務の配置（オーケストレーション）

| 新規ファイル | 責務 |
|---|---|
| `services/llm_client.py` | `LlmClient` Protocol ＋ `NoopLlmClient` ＋ 実装1つ。`push_sender.py` と同型 |
| `services/deep_reading_service.py` | 同意・課金・冪等・ガード・フォールバックの手順をまとめる |
| `config.py` の `DeepReadingConfig` | `mode`（`noop` 既定／`llm`）、モデル名、タイムアウト、最大文字数、APIキー（環境変数） |

`orchestrator.py` に `_build_llm_client()` を追加する。`runtime_mode` が production で
`mode=noop` なら警告を出す（`_build_push_sender` と同じ書き方）。

### 3.3 失敗が見える出口を作る

握り潰しを作らない。結果に**状態**を持たせ、画面が区別できるようにする。

| `deep_reading_status` | 意味 | 画面の出し方 |
|---|---|---|
| `none` | 未実行 | ボタンを出す |
| `applied` | 推敲済み | 推敲後の本文を表示 |
| `unavailable` | 提供準備中（`mode=noop`） | 「準備中」＝押せない |
| `failed` | 実行したが失敗（通信・タイムアウト） | 「取得できませんでした」＋再試行。**消費なし** |
| `rejected` | 生成文が検査に落ちた | 内蔵の本文のまま。利用者には `failed` と同じ見え方。理由はログと監査へ |

「0件」と「取れなかった」を同じ表示にしない。

### 3.4 課金（新しい判定ロジックを作らない）

`スプレッド定義` シートへ `kind = "option"` の行を1本足し、
`required_tickets` と `allowed_plans` をそこで決める。
`BillingService` の既存3メソッドをそのまま使えるため、**課金の分岐は1つも増えない**。

- 枚数は引かないため `card_count = 0`。ただし**フリーリーディングの可変枚数と混ざらない**よう、
  `kind == "option"` は種別選択・スプレッド選択の一覧から除外する（`readingSpreads` の絞り込みを
  `kind == "reading"` に厳密化する。現在は `!isOracle` で、追加すると紛れ込む）。
- シートの追記は `scripts/extend_reading_db.py` に足す。**オーナーのxlsx編集は不要**。

> 代替案: `config.py` に枚数を持つ（`free_daily_draw_limit` と同じ場所）。実装は軽いが、
> 第1段で「枚数と課金をコードから追い出す」と決めた方針に反するため**非推奨**。

**消費の順序**: 生成が成功し、検査も通ってから消費する。失敗時の返却処理を作らない。
同じセッションに対する2回目は**再生成せず保存済みを返す**（冪等・二重課金の防止）。

### 3.5 同意（プライバシー）

- `User` に `deep_reading_consented_at: datetime | None` を追加する。
- 未同意なら API は `403` と同意要求を返し、**実行しない**。
- 画面は初回のみ同意ダイアログを出す。文面で「**相談内容と結果の本文が外部のAI事業者へ送られる**」ことを明示し、
  プライバシーポリシーへのリンク（`apps2craft.com/oracle/privacy.html`）を置く。
- 同意の取得・撤回は監査ログへ残す。

### 3.6 生成文の検査（承認方針 §7.3-2 の履行）

内蔵エンジンに検査を置き、次のいずれかに触れたら `rejected` とする。

1. 適用トーンの `avoid`（マスタ由来）を含む
2. 断定的な助言語（診断・治療・投資・法律）に該当する語を含む — 検査語は**マスタへ新設**し、コードに直書きしない
3. 文字数が上限を超える／空

### 3.7 送るもの・送らないもの

| 送る | 送らない |
|---|---|
| 相談内容、内蔵エンジンの本文、カード名・キーワード・ポジション名、テーマ名 | 利用者ID、ニックネーム、メールアドレス、端末情報、購入情報、履歴 |

プロンプトは `InterpretationEngine` が組み立てる。**サービス層が素の文字列を継ぎ足さない**
（送信内容の単一真実源を1か所にする）。

### 3.8 API（`05_API仕様書.md` へ追記する）

```text
POST /reading/{session_id}/deep
  req : { "user_id": str }
  res : ReadingResultResponse（deep_text と deep_reading_status を含む）
  403 : 未同意／対象プラン外／チケット不足
  400 : 結果が未生成／セッション不明

POST /account/deep-reading-consent
  req : { "user_id": str, "consented": bool }
  res : { "consented_at": datetime | null }
```

`GET /reading/{id}` と `/copy` の応答にも `deep_text` / `deep_reading_status` を足す
（`_map_result` の1か所で済む）。

### 3.9 画面（UI設計資料との対応）

推敲結果は本文の差し替えではなく**追記**とし、利用者が元の文章も読めるようにする。

> 申し送り: `07_UI画面遷移_ワイヤーフレーム仕様書.md` の画面ID対応表（U-01〜U-19）は、

## 4. リスク

### 4.1 金銭・課金

1. **二重課金**: 同一セッションで2回押される。→ 冪等化（保存済みがあれば再生成しない）で塞ぐ。
2. **失敗したのに消費**: 通信断・タイムアウト。→ 成功・検査通過の後に消費する順序で塞ぐ。
3. **費用の暴走**: 1回あたりの入力が相談内容3000字＋本文。→ 入力・出力の上限を設定に持ち、超過は送信前に切る。上限は `DeepReadingConfig`。

### 4.2 システム

1. **UIが固まる**: 応答が数秒〜数十秒。→ タイムアウトを設定（既定20秒）。画面は進捗表示で操作を止めない。
2. **レート制限・障害**: 事業者側の429/5xx。→ 再試行は1回まで。失敗は `failed` として見せる（握り潰さない）。
3. **個人情報の混入**: プロンプト組み立てを複数箇所でやると、いずれ利用者IDが混ざる。→ 組み立てを `InterpretationEngine` の1メソッドに限定し、**送信内容をテストで固定**する。

### 4.3 運用

1. **ポリシー未改定のまま公開**: 審査で止まる／信義則上の問題。→ `mode=llm` かつポリシー未改定を**起動時に検出できない**ため、リリース手順書へ明記し、テストで「同意なしでは実行されない」ことを固定する。
2. **本番で noop のまま**: ボタンだけ生きて何も起きない。→ `runtime_mode=production` かつ `mode=noop` で起動時に警告（既存2連携と同じ）。画面は `unavailable` を出す。
3. **文章の品質低下**: 推敲で世界観が壊れる。→ 検査で弾いた場合は内蔵の本文へ戻す。採用・却下の件数をログに残す。
