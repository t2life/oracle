### 1.2 iOS で効くか — メーラー起動（`mailto:`）

`inquiry_screen.dart` L86-99 は `launchUrl(uri, mode: LaunchMode.externalApplication)` を呼び、
失敗したら宛先をスナックバーで見せる。iOS 側のプラグインの実装は次のとおり。

- `url_launcher_ios` 6.4.2 の `launchUrl` は **`canOpenURL` を通らず** `UIApplication.open` を直接呼ぶ
  （`URLLauncherPlugin.swift` L35-47。`canOpenURL` を使うのは `canLaunchUrl` の側だけ）
- ∴ iOS 9 以降の「独自スキームの事前申告」（`LSApplicationQueriesSchemes`）は**不要**。
  `Info.plist` に追記しなくても `mailto:` は開く
- メールアプリが1つも無い端末（利用者が Mail を削除した場合・シミュレータ）では `open` が false を返し、
  既存の「宛先を文字で見せる」経路に落ちる。**黙って失敗しない**

環境情報（`_environment()`）は `dart:io` の `Platform.operatingSystem` / `operatingSystemVersion` だけを使う。
iOS でも取得でき、`ios` と `Version 26.6.1 (Build 23G83)` の形で本文に載る。

∴ **iOS 側にコード変更は要らない。** 実機で「メールアプリが開き、件名・本文・宛先が入っていること」を見るだけでよい。

### 1.4 シャッフル音

前回の3案（神楽鈴風・風のうねり・低音の持続音）は**すべて却下**。
ご指示は「**シャラシャラと細かな粒子が擦れ合う音**」。

現行 `shuffle.wav` は乱数ノイズを滑らかにならした音（`_noise_swish`）で、
粒立ちが無く「サー」という帯域ノイズに寄る。粒の音にするには、
**ごく短い音の粒を多数まく**作り方（粒状合成）に変える必要がある。

## 3. 作業3: 方針

### 3.1 鳴らし方（前回方針のまま・再掲）

- シャッフル段階で最初に指が触れたとき、`playAmbience(OracleSound.shuffle, loop: true)` で**1本のループを開始**
- シャッフル完了（集める音の直前）と画面離脱（`dispose`）で `stopAmbience()`
- 指の動きごとの `play(OracleSound.shuffle)` は削除。振動は現行どおり 170ms ごと
- 前回足した `SoundService.play` の `restart` 引数は不要になるため**削除**

### 3.2 音源 — 細かな粒子が擦れ合う音（3案・試聴用）

作り方は「ごく短い粒（数ミリ秒の高域のはじけ）を、1秒あたり数百個、不規則にまく」。
粒の長さ・密度・明るさを変えた3案を用意した（いずれも6秒で継ぎ目なくつながる。試聴は3回つないだ18秒版）。

| 案 | 粒の大きさ・密度 | 聞こえ方 |
|---|---|---|
| D 細粒 | 約7ms・毎秒520粒・明るめ | 砂や細かいビーズが一定に擦れる。**最も「シャラシャラ」に近い** |
| E 中粒 | 約16ms・毎秒260粒・やや太い | 数珠や貝のかけらが触れ合う。密度が3秒周期でゆっくり増減する |
| F 細粒＋うねり | 約8ms・毎秒600粒 | 波打ち際の砂利のように、2秒周期で寄せて返す |

いずれも既存の効果音と同じ**仮の合成音**である。正式素材（実録のシャッフル音・砂の音など、利用許諾のあるもの）が
用意できれば、`shuffle.wav` として置くだけで差し替わる（4〜8秒程度・先頭と末尾がつながる音が望ましい）。

選ばれた案の合成を `scripts/generate_sound_assets.py` の `gen_shuffle()` に反映し、
`mobile_app/assets/sounds/shuffle.wav` を作り直す（生成元を1か所に保つ）。

### 3.4 iOS の配布方式（判断をお願いする）

| 方式 | 要るもの | 向き |
|---|---|---|
| TestFlight | App Store Connect にアプリを登録（＝**Bundle ID の確定が前提**）、App 用の情報入力、ビルドのアップロード | 本番の配布経路と同じ。テスターは招待メールから入れる。**提出前の確認に近い形で試せる** |
| Firebase App Distribution（iOS） | ad hoc プロビジョニング。**テスターの端末 UDID をそれぞれ登録**し、そのたびに再ビルド | Android と同じ運用にそろう。ただし端末登録の手間がある |
| 手元の実機のみ（現状） | Mac と USB 接続 | 今の確認はこれで足りている |

Android は Firebase App Distribution で配り終えているが、iOS で同じ方式にすると端末登録の運用が増える。
**Bundle ID を確定して TestFlight を用意する**のが本筋だと考える（引き継ぎ書 §2.1 の判断が前提になる）。
