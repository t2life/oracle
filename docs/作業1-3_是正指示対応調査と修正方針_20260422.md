## 3. 作業2: 関連ファイル調査（配線・責務）

### 3.1 backend オーケストレーション

配線:

- `main.py` -> `api.py` -> `orchestrator.py` -> services -> `store.py`
- `schemas.py` はAPI DTO責務に限定。

責務評価:

- サービス分離は良好。
- 永続化層が未分離で `InMemoryStore` に集中。
- 本番運用必須のDB/Redis連携は未着手。

### 3.2 mobile オーケストレーション

配線:

- `main.dart` -> `app.dart` -> `app_router.dart` -> 各 screen
- `api_client.dart` は一部APIのみ実装。

責務評価:

- 画面責務は分割済み。
- 状態管理層（共通アプリ状態）が存在せず、実導線の一貫管理が不能。
- UI要件に対し「情報表示骨格」中心で業務動作が不足。

### 3.3 admin オーケストレーション

配線:

- `app/*` -> `lib/api.ts` -> backend `/admin/*` と `/cards`
- `components/nav-shell.tsx` で共通ナビを統一。

責務評価:

- ページ責務は整理済み。
- 認証トークン管理はローカル保存のみで本番保護不足。
- 依存の脆弱性対応未了。

### 3.4 既存設定流用可否

- backend設定は `AppConfig` に集中しているため、DB/Redis設定も同一箇所へ拡張すべき。
- モバイルのAPIベースURL・状態管理パラメータは新規乱立ではなく `core` 配下集約が適切。
- adminの環境値は `NEXT_PUBLIC_API_BASE_URL` を継続利用可能。

### 3.5 問題のコードレベル原因

1. `InMemoryStore` 固定により、再起動後データ整合が失われる設計。
2. mobile がプレースホルダ画面群中心で、API呼び出しと状態遷移が断絶。
3. admin依存の安全化プロセス（auditを完了条件とする更新）が未実施。
4. 仕様画面IDと実装IDのズレ（U-19の意味不一致）。

## 4. 作業3: 修正方針（コーディング前方針）

### 4.1 方針A: admin_app 依存更新

対象:

- `admin_app/package.json`
- `admin_app/package-lock.json`
- 必要に応じて `admin_app/tsconfig.json`（自動補正分を保持）

方針:

- `npm audit` で high/critical 0 を目標。
- lint/buildで互換性確認。

### 4.2 方針B: mobile_app 実APIバインド + 状態管理

対象（主要）:

- `mobile_app/lib/core/network/api_client.dart`
- `mobile_app/lib/core/state/*`（新規）
- `mobile_app/lib/app.dart`
- `mobile_app/lib/core/routing/app_router.dart`
- U-03/U-04/U-05/U-06/U-07/U-08/U-09/U-10/U-13/U-17/U-18/U-19 画面

方針:

- `ChangeNotifier` ベースの単一アプリ状態を導入。
- 認証、テーマ、デッキ、占いセッション、履歴、課金、問い合わせを一貫管理。
- 既存プレースホルダは削除せず段階置換し、ルーティング互換を維持。
- ローディング、エラー表示、再試行、未ログイン制御を全対象画面に実装。
- U-19 を問い合わせ画面に修正し、仕様整合を回復。

### 4.3 方針C: PostgreSQL/Redis 移行着手

対象:

- `src/oracle_app/config.py`
- `src/oracle_app/persistence/*`（新規）
- `src/oracle_app/cache/*`（新規）
- `scripts/init_persistence.py`（新規）
- `requirements.txt`

方針:

- 現行の `InMemoryStore` を壊さず、永続化の土台を追加する。
- ORMモデル、DB初期化、Redis接続方針、初期データ投入入口を追加。
- 主要導線の回帰を避けるため、既定は現行ストアを維持しつつ移行可能性を実装。

### 4.4 影響分析

- API影響:
  - mobile側の実API接続化で、既存API呼び出し頻度とエラー経路が増える。
  - 問い合わせ導線の実装で `/inquiries` の利用が増える。
- 管理画面影響:
  - 依存更新でビルド環境要件が変わる可能性。
- 課金/履歴影響:
  - mobileでの復元・履歴読み込み経路が本番同等に近づく。
- 通知/分析影響:
  - mobileからの通知登録・イベント送信を次段の運用強化へ接続しやすくなる。
- 外部導線影響:
  - U-13/U-17/U-18/U-19の画面実装に伴い導線テスト観点が増える。

### 4.5 リグレッション抑止

- backend既存API契約を変更しない。
- 既存pytest観点（10件）を維持し、必要観点を追加。
- 影響が大きい変更は新規モジュール追加で段階導入し、既存責務を崩さない。
