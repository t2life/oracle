  - HybridStore による段階導入は開始されているが、全ドメインへの完全永続化置換および本番運用レベルの監視・フォールト検出は未完である。[file:364]

## 3. 是正の基本方針

本ラウンドでは、次の 3 点を優先是正事項とする。[file:364]

1. モバイルUI 未完画面（U-12/U-14/U-15/U-16）の本実装
2. HybridStore から完全永続化への拡張
3. 最小限の CI/CD・監査ログ・運用自動化の着手

これらは、詳細仕様書および UI 設計資料で定義された体験・運用レベルに近づけるために必須であり、次フェーズの総合受入試験の前提条件と位置付ける。[file:356][file:357][file:358]

## 5. 指示2：HybridStore から完全永続化への拡張

### 5.1 現状整理

- `postgres.py` / `redis_cache.py` / `hybrid_store.py` / `init_persistence.py` により、結果・履歴を中心とした段階永続化が開始されている。[file:364]
- `config.py` の永続化設定により、永続化有効時は HybridStore を起動し、失敗時は InMemory にフォールバックする挙動が実装されている。[file:364]

### 5.2 実施内容

1. 永続化対象ドメインの拡張
   - 現在の結果・履歴に加え、少なくとも以下のドメインを PostgreSQL 上で永続化すること。[file:356][file:359]
     - users
     - subscriptions
     - ticket_wallets
     - announcements
     - inquiries
   - 可能であれば、decks/cards/themes などのマスタも段階的に永続化し、インメモリマスタとの二重管理を解消すること。
2. HybridStore の役割整理
   - 本番運用モードでは、PostgreSQL/Redis を必須とし、InMemory をローカル開発および自動テスト専用モードに限定する設計を明確化すること。[file:364][file:358]
3. マイグレーションおよびロールバック手順の整備
   - DB スキーマのマイグレーションスクリプトを整備し、バージョン管理すること。
   - 想定外の問題発生時に旧バージョンへ戻せるロールバック手順を用意すること。
4. 再起動・障害時挙動の確認
   - サーバ再起動後も履歴、課金状態、お知らせ、問い合わせ等の主要データが保持されていることを確認すること。[file:361]
   - DB や Redis の一時停止・復旧シナリオにおいて、アプリがどのように振る舞うか（エラー文言、リトライ、フォールバック）を検証し、ログで追跡可能にすること。

### 5.3 提出物

1. 永続化対象一覧と移行マッピング表
   - 各ドメインについて、現状の InMemory 管理との対応関係および PostgreSQL 上のテーブル定義を一覧化した表。
2. マイグレーションスクリプト一式と実行手順
   - マイグレーションコマンド、適用順序、ロールバック手順を含むドキュメント。
3. 永続化試験レポート
   - 再起動試験、DB停止・復旧試験の実施内容と結果、検出された課題と対処内容を記載したレポート。

### 5.4 完了条件

- 本番モード設定時、占い結果・履歴・課金状態・お知らせ・問い合わせがすべて PostgreSQL 上で永続化されていること。[file:364][file:356]
- InMemory ストアは、開発・テスト用途に限定され、本番環境では利用されない構成となっていること。[file:364][file:358]

## 6. 指示3：最小限の CI/CD・監査ログ・運用自動化の着手

### 6.1 実施内容

1. CI パイプラインの構築
   - ソースコードリポジトリに CI 設定（例：GitHub Actions 等）を追加し、以下を自動実行すること。
     - バックエンド pytest
     - `scripts/smoke_test.py`
     - `scripts/init_persistence.py`（永続化設定での初期化確認）[file:364]
2. 監査ログの導入
   - バックエンド主要 API のうち、少なくとも以下の操作について、誰がいつ何を実行したかを追跡可能な監査ログを導入すること。[file:358][file:361]
     - 認証（ログイン／ログアウト）
     - 課金関連（購入検証、復元、サブスク状態変更）
     - 管理画面操作（お知らせ登録、通知配信、カード・デッキ・テーマ更新など）
3. ヘルスチェックと監視設定
   - バックエンドのヘルスチェックエンドポイントを明確化し、ステージング／本番で監視可能な状態にすること。
   - 監視対象（レスポンスコード、レイテンシ、エラー率など）と閾値を定義すること。

### 6.2 提出物

1. CI 設定ファイル
   - CI ツールの設定ファイル（YAML 等）および実行結果のサンプルログ。
2. 監査ログ設計メモ
   - どのイベントをどの粒度で、どのストレージに、どの保持期間で保存するかを示す簡易設計メモ。
3. 監視設定一覧
   - ヘルスチェック URL、監視項目、閾値、アラート条件を記載した一覧表。

### 6.3 完了条件

- 任意のブランチへの push（または PR 作成）に対し、CI が自動実行され、失敗時に検知可能な状態になっていること。
- 認証・課金・管理操作に対して、少なくとも最低限の監査ログが記録され、後から事象を追跡可能であること。[file:358][file:361]

## 7. 実施順序とスケジュール前提

是正は、次の順序で進めることを推奨する。[file:364][file:358]

1. HybridStore 永続化拡張（DB スキーマ・マイグレーション整備を含む）
2. モバイルUI 未完画面の本実装（永続化環境を前提とした動作確認を兼ねる）
3. CI/CD・監査ログ・監視設定の導入

順序の変更が必要な場合は、その理由と影響範囲を明示した上で、事前に協議・承認を行うこと。
