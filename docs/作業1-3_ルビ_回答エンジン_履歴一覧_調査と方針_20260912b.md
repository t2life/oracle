# 作業1-3 ルビ・回答エンジン・履歴一覧 — 調査と方針

作成日: 2026-09-12
ご指摘（実機確認より）:

1. 託宣結果・リーディング画面の**本文に神名のルビが無い**。該当箇所は全てルビを付ける
2. **質問に対する回答が完結しておらず、マスタやカードのキーワードを羅列しているだけに感じる。**
   AIのように文脈の意図を読み取り正しく回答するエンジンをアプリに実装したい
3. 履歴画面を**一覧（種別＋日時の1行）→ タップで詳細**に変える。件数が増えると視認性が落ちるため

## 1. ① 神名のルビ

### 1.1 事実

ルビ（`reading`＝アメノミナカヌシ等）はカードマスタに**44柱すべて揃っている**。
しかし表示しているのは**札の絵と見出しだけ**で、託宣文の本文には入っていない。

| 箇所 | ルビ | 実装 |
|---|---|---|
| カード図柄パネル | あり | `OracleCardFace(reading: …)` |
| 結果画面の位置別カード見出し | あり | `reading_result_screen.dart` L499 `rubyOf()` |
| **託宣文の本文** | **無い** | `InterpretationEngine._fill_placeholders` の `{神名}` が `name_ja` のみ |
| **組み合わせ解釈の本文** | **無い** | `compose_combination` が `name_ja` を直接連結 |

∴ 本文は**エンジンが組み立てた1本の文字列**なので、直すのはエンジン側である
（画面側でルビを後付けすると、読み上げ・履歴・共有と食い違う）。

### 1.2 方針

`{神名}` の差し込みと組み合わせ解釈で `須佐之男命（スサノオノミコト）` の形にする。

- **多言語の心配はない**。本文（`compose_reading`）は日本語専用で、
  en/zh はカードマスタの訳文をそのまま使っている（`reading_service.py` L264-269）
- ルビが空のカードは**括弧を出さない**（fail-soft）
- 読み上げ（TTS）は括弧内を読んでしまうため、**読み上げ用は従来の文**を渡す

> **ご確認いただきたい点**: 3枚引きでは同じ神名が本文に2〜3回出る
> （【未来】の見出しと組み合わせ解釈など）。**毎回ルビを付けるか、初出だけにするか**。
> 読み物としては初出だけが一般的だが、ご指示は「該当箇所は全て」であるため案は全出現とした。

## 2. ② 回答が完結していない

### 2.1 事実 — 何が「羅列」に見えているか

`services/interpretation_engine.py` L237-240

```python
def _as_phrase(text: str) -> str:
    """体言止めの列挙（「A。B。C。」）を、文へ埋め込める句（「A、B、C」）にする。"""
```

カードマスタの `theme_meanings` は**3つの体言止めの列挙**である。

| カード | `theme_meanings.money` |
|---|---|
| 須佐之男命 | 大胆な改革。破壊的イノベーション。古いシステムを壊して新しい方法へ。 |

`_as_phrase` はこれを `、` で繋ぐだけなので、**3つ全部がそのまま本文へ出る**。

```text
【過去】須佐之男命。ここまでのあなたは、大胆な改革、破壊的イノベーション、
古いシステムを壊して新しい方法へという流れの中にいました。
```

∴ 「羅列に見える」のは錯覚ではなく、**マスタの列挙を無編集で流している**ためである。
これは3枚引きなら3回、組み合わせ解釈でさらに1回繰り返される。

### 2.2 事実 — 何が「回答していない」か

現行エンジンは次の順で段落を並べるだけで、**問いの中身を一度も使っていない**。

```text
導入（問いを引用するだけ） → 各カード → 組み合わせ → 文脈/問いの扱い → 助言 → 締め
```

問いの文字列が本文に効くのは
①導入の引用 ②ジャンル・状況の分類（キーワード一致）③番号の読み（期日・数量）
④問いの扱い（運任せ・分類外）の4箇所だけで、いずれも**分類**である。
「ロト7で1等」という**中身**は、どこにも入らない。

∴ **現行エンジンは構造上、問いに答えることができない。**
分類器であって、読解器ではない。

### 2.3 二つを分けて考える

| | 症状 | AIなしで直るか |
|---|---|---|
| (a) | キーワードの羅列 | **直る**。設計の欠陥であり、AIの有無と無関係 |
| (b) | 問いの中身に答えない | **原理的に無理**。自由文の読解が要る |

**(a) はどちらの道を選んでも直すべきである。** 以下 (b) の選択肢を示す。

### 2.4 選択肢

#### A案: 生成AIで文章を作る（ご要望そのもの）

サーバー側で、カードの素材＋問いを渡して文章を書かせる。

| 項目 | 内容 |
|---|---|
| できること | **問いの意図を読み、それに答える**。「ロト7」「1等」に触れた文になる |
| 構成 | 素材（カード・位置・属性・エレメント・キーワード）と問いを渡し、**素材の外を語らせない**指示を付ける |
| 安全 | 生成後に `禁止表現マスタ`（22語）で機械検査。引っかかれば**現行エンジンの文へ落とす**（fail-soft） |
| オフライン | **現行エンジンのまま**。AIはサーバー側の上乗せ層とし、パリティの規律は壊さない |
| 費用 | 1リーディングあたり 入力 約1,500字＋出力 約800字。小型モデルなら**1回あたり1円未満**の水準。月額550円プランでも成立しうるが、**契約時に実価格の確認が必要** |
| 審査 | Google Play に**生成AIコンテンツの専用ポリシー**があり、不適切な出力を防ぐ責任と通報手段の提供が求められる |
| 規約 | プライバシーポリシーを **Ver.1.4** へ（AI事業者への提供を再記載。Ver.1.2→1.3 で消した箇所を戻す） |
| 通信 | オンライン必須。機内モードでは現行の文になる |

> **前回（2026-09-11）に外部AIを取りやめた理由との関係**
> あのときは「ディープリーディング」という**仕様に無い機能のため**だけにAIが要る構図で、
> 対価が釣り合わなかった。今回は**本文の品質そのもの**が要件であり、前提が違う。
> 取りやめの判断と矛盾しない。

#### B案: ルールを深くする（AIを使わない）

| 変更 | 内容 |
|---|---|
| 羅列をやめる | `theme_meanings` の3つから**1つだけ**選ぶ（カードIDと位置で決定的に）。段落ごとに違う1つが出る |
| 問いの語を使う | 問いから主題語（ロト7・転職・彼 など）を1語取り出し、結論文で**そのまま使う** |
| 構成を変える | いまの「並べるだけ」から **結論 → 根拠（カード）→ 助言** の順へ |
| 意図の種類を増やす | いまの19分類に加え、**問いの型**（可否・時期・方法・選択・気持ち・原因）を判定して結論文の型を変える |

**できること**: 「ロト7については、いまは〜という流れです」まで言える。
**できないこと**: 問いの事情（前回外した・家族に反対されている等）を汲むこと。
型の外の問いは、やはり一般論になる。

#### C案: B案を土台に、A案を上乗せ

Bで素材と構成を整え、AIは**文章化だけ**を担当する。
AIが落ちても B の文が残るため、品質の下限が上がる。費用はAと同じ。

### 2.5 推奨

**C案。** ただし段階を分ける。

| 段 | 内容 | 承認 |
|---|---|---|
| 第1段 | **(a) 羅列の解消** ＋ B案の構成変更 | AIの判断と無関係に先行できる |
| 第2段 | A案（生成AI）の追加 | 費用・規約・審査の判断が要る |

第1段だけでも、いまの画面はかなり変わる。第2段は第1段の出来を見てから判断できる。

## 3. ③ 履歴画面を一覧＋詳細へ

### 3.1 事実

`features/history/presentation/history_screen.dart` L73-76

```dart
title: Text(item.summary),
subtitle: Text('${item.createdAt}\n${item.fullText}'),
isThreeLine: true,
```

**全文（`fullText`）を一覧に出している。** 3枚引きなら1件で800字を超えるため、
ご指摘のとおり件数が増えると読めなくなる。

さらに、履歴は**種別（託宣／リーディング）を持っていない**。

| 層 | 種別 |
|---|---|
| `models.HistoryItem` L206-216 | 無し |
| `schemas.HistoryItemResponse` L202-211 | 無し |
| `HistoryItemModel`（Dart） | 無し |

### 3.2 方針

| # | 変更 |
|---|---|
| 1 | `HistoryItem` に **`spread_id`** を追加（`daily`＝託宣／それ以外＝リーディング）。**新しい概念を作らず既存のスプレッドIDを使う** |
| 2 | 一覧は **「託宣／リーディング」＋「YYYY/M/D HH:MM」** の1行。全文は出さない |
| 3 | タップで**詳細画面**（U-22 新設）。全文・カード・削除・読み上げは詳細側へ |
| 4 | 削除は詳細画面へ寄せる（一覧のゴミ箱を押し間違える事故を避ける） |

> 既存の履歴には `spread_id` が無い。読めなかったものは **`daily` 扱い**とし、
> 「託宣」と表示する（欠損で画面が壊れない）。

日時は現在 ISO 文字列のまま表示しているため、**JSTで `YYYY/M/D HH:MM` に整形**する。

## 5. リスク

### 占いとしての妥当性

1. ルビの繰り返しで読みにくくなる → 全出現か初出のみかを承認事項アで確定
2. 意味を1つに絞ることで情報が減る → 3枚引きなら段落ごとに違う1つが出るため、**全体では3つとも出る**
3. （A案を採る場合）AIが素材の外を語る → 禁止表現の機械検査＋現行文へのfail-soft

### システム

1. ルビでパリティ期待値が全ケース変わる → 生成し直し、サーバーとオフラインの一致をテストで固定
2. 履歴に列を足す → 既存データは `daily` 扱い（欠損で壊れない）
3. （A案を採る場合）オフラインとの文章差 → AIはサーバー層の上乗せとし、オフラインは現行エンジンのまま

### 運用

1. （A案を採る場合）費用が利用量に比例 → 月額プランの原価に効く。実価格の確認が要る
2. （A案を採る場合）ストア審査 → Google Play の生成AIポリシーへの対応（通報手段・不適切出力の抑止）
3. 履歴の詳細画面が増える → 画面ID表（`07_UI画面遷移_ワイヤーフレーム仕様書.md`）の更新が要る（既に他5画面も未反映）
