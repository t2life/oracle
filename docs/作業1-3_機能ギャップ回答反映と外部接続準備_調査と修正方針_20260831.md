## 4. 作業3: 修正方針

### WP-A: テーママスタの6軸是正（オーナー回答2）【要承認】

- **原因**: `config.py:default_theme_ids` が企画書時点の9軸のまま。オーナー確定の6軸（仕事・恋愛・健康・金運・潜在意識・ハイヤーセルフ）を反映していない。
- **変更ファイルと内容**:
  - `config.py`: `default_theme_ids` を6軸へ変更
    （`work`, `love`, `health`, `money`, `subconscious`, `higher_self` の宣言順=表示順）。
    レガシー5軸は新設タプル `legacy_hidden_theme_ids`
    （`relationships`, `soul`, `awakening`, `karma`, `past_life`）として保持。
  - `store.py:_seed_master_data`: `theme_name_map` に
    `money`=「金運」（「お金」から名称変更）、`subconscious`=「潜在意識」、
    `higher_self`=「ハイヤーセルフ」を追加。6軸は `is_visible=True`、
    レガシー5軸は `is_visible=False` でシード（**削除しない**）。
  - `tests/test_billing_and_limits.py`: theme_id の awakening/soul/karma を
    可視6軸のIDへ更新（マスタ仕様変更に伴う正当な追随。テスト合格のための本体改変ではない）。
  - 新規テスト: `GET /themes` が6件・宣言順で返ること、レガシーIDでの
    `/reading/start` が400になること、`GET /admin/themes` に非表示レガシーが残ること。
- **レガシーを非表示温存する理由**: 履歴・結果データは `theme_id` を保持しており、完全削除すると過去データの参照整合とカード解釈シード（`meanings_by_theme`）が壊れる。非表示化なら U-05 に出ず、`/reading/start` は `is_visible` 検査で自然に拒否される（既存分岐を流用、新規ガード不要）。
- **画面影響**: U-05（テーマ選択）は動的取得のため自動反映。A-03（テーマ管理）は可視列で状態が見える。U-10履歴はtheme_id表示のため非破壊。
- **API影響**: `/themes` の件数と名称のみ変化。課金・通知・履歴・管理画面のAPIシグネチャ変更なし。

### 4.1 今回スコープ外（理由付き見送り）

| 項目 | 見送り理由 |
|---|---|
| スプレッド多様化（ケルト十字等） | 企画書スコープ外の拡張。オーナーの商品企画判断が先 |
| ソーシャル機能（SNS共有等） | 機能ギャップ指摘書自身が「初期MVPでは後回しが正当」と判定済み |
| オフライン占い | サーバー抽選の設計原則（課金整合・抽選の公正性）と衝突。「意図的非対応」として仕様書明記を提案 |
| マスタのPostgres化（A-2） | 影響範囲が大きく、本ラウンドのAPI変更と混ぜるとリスク増。次ラウンド独立実施を推奨 |
| Lottie演出の実装 | Flutter SDK未導入でビルド検証不可。今回は仕様明文化のみ、実装は検証環境確保後 |
| 実URL設定（B-4） | ショップ/鑑定/ライブの実URLが未提供。ユーザー提供待ち |
| FCM/Apple実接続 | 認証情報未提供。WP-F/WP-Gで「config切替だけで接続できる状態」まで準備 |

### 4.2 リスク評価（課金・システム・運用 各3点以上）

**課金リスク**:

1. 検証器挿入位置の誤りによる二重付与 → 冪等チェックを検証通過後に維持し、既存テスト（⚡機能5相当）で担保。
2. `subscription_expires_at` 公開により期限計算バグが可視化される可能性 → 期限値はJSTで返却し、テストで境界（期限切れ→FREE降格後はnull）を確認。
3. localモードのまま本番運用してしまう検証すり抜け → productionでの起動拒否ガード（⚡機能8と同型）。

**システムリスク**:

1. `extra="forbid"` はリクエスト側の防御であり、レスポンスへのフィールド追加はモバイル（明示キー参照）に非破壊であることを確認済み。ただし将来のフィールド**削除**は破壊的なため仕様書に注記。
2. テーマID変更による参照整合 → レガシー非表示温存方式で履歴・解釈シードを保全。テストの追随更新を同時実施。
3. 権限制御追加による管理画面403退行 → 既定super_adminは全権のため不変。新ロールは新規シードのみで既存動線に影響しない。

**運用リスク**:

1. Noop配信の「送ったつもり」 → レスポンスmessageとWARNINGログで実配信モード未設定を明示。
2. ロール誤設定による操作不能 → super_adminを常設し、ロール変更はシード定義（config/store）で管理。
3. 仕様書と実装の再乖離 → 承認後、`12_実装ロジック機能一覧.md` と `10_仕様準拠状況_総合対応表.md` を同一コミット単位で更新。
