## 2. お問い合わせのメーラー化

### 2.1 なぜ変えたか

従来はサーバーの `/inquiries` へ送っていた。∴ サーバーが未公開の状態では
**送信ボタンごと無効**になり、テスターは問い合わせる手段が無かった。

メールアプリに委ねれば、その制約が消える。これは妥協ではなく、
この構成での最良である（先行アプリの判断をそのまま採る）。

- **返信先**: 利用者自身のメールアプリから出るため、**送信元がそのまま返信先**になる。
  アドレスを入力させる必要も、入力ミスで届かない心配も無い
- ∴ **メールアドレス入力欄を削除**した

### 2.2 設計（先行アプリからの移植）

| 原則 | 実装 |
|---|---|
| 組み立ては1箇所 | `core/support/inquiry_form.dart`。画面に直書きしない |
| 件名にアプリ名を前置 | `[日本神話オラクルロンカード] 不具合` |
| 端末・版数を自動付記 | 本文末尾へ。切り分けに要るが、利用者に毎回書かせるのは酷である |
| 記入例は**プレースホルダ** | 既定値にすると消し忘れが送られ、読む内容が例文で埋まる |
| 上限4000字・残りは負で表示 | 0で頭打ちにしない（何文字削るか分からなくなる） |
| 失敗時は**宛先を文字で示す** | 黙って何も起きないのが最悪 |

### 2.3 多言語

先行アプリは共有層に日本語を持つが、本アプリは ja/en/zh の3言語である。
∴ **`InquiryForm` に文言を持たせず、localized な文字列を引数で受け取る**。
件名・本文・記入例・注記はすべて画面が `AppLocalizations` から渡す。

### 2.4 `mailto:` の組み立て

`Uri(queryParameters: …)` は空白を `+` にするが、`mailto:` の本文で `+` は
空白に戻らずそのまま文字として届くメーラーがある。
∴ `Uri.encodeComponent`（空白は `%20`）で自分で組む。

### 2.5 版数の持ち方

本文へ載せるアプリ版数のために `package_info_plus` を足すことはしなかった
（iOS 移植を控えており、依存を増やすと結合の確認が増えるため）。
`AppLinks.appVersion` に写しを置き、**`pubspec.yaml` と一致することをテストで機械照合**する。

### 2.6 不要になったコードの削除

画面が使わなくなった `submitInquiry` を4ファイルから完全に削除した
（インターフェース・ApiClient・OfflineBackend・AppState）。
サーバー側の `/inquiries` と管理画面は他に利用者がいるため残す。

## 3. 署名鍵

### 3.1 作ったもの

| ファイル | 内容 |
|---|---|
| `mobile_app/android/upload-keystore.jks` | PKCS12・RSA2048・有効期限30年・alias `upload` |
| `mobile_app/android/keystore.properties` | パスワードと別名 |

いずれも **`.gitignore` で除外**。写しを `（リポジトリ外）_署名鍵バックアップ/` に
README（指紋・復元手順・限界）つきで置いた。

> JKS ではなく **PKCS12** にした。JKS は `keytool` が毎回
> 「独自形式である」と警告するため。Gradle・Android とも PKCS12 を扱える。

### 3.2 ビルド設定

先行アプリと同じ形にした。**`keystore.properties` が在るときだけ**リリース署名を作り、
無ければ debug 署名のままにする。

```kotlin
signingConfig = signingConfigs.findByName("release")
    ?: signingConfigs.getByName("debug")
```

鍵の無い開発機やCIでビルドが落ちると原因が分かりにくいため、落とさない。
∴ **配布ビルドは必ず鍵が在る環境で作る**（手順書 §6.1 に明記）。

### 3.3 切り替えの代償（実測）

debug 署名の版が入った実機へリリース署名の版を入れようとすると
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` になる。開発機で実際に踏んだ。
テスターは初回配布のため影響しない。

### 4.1 ★グループ宛にしなかった理由

`testers` グループには先行アプリのテスター `inamasutakashi@gmail.com` が含まれる。
グループ宛に配ると**ご指定外の相手にも届く**。∴ `--testers` で個別に指定した。

### 4.2 配布ビルドで外したもの

| 外したフラグ | 付けたままだとどうなるか |
|---|---|
| `--dart-define=PREMIUM_UNLOCKED=true` | 起動時に有料機能が全解放され、課金導線を検証できない |
| `--dart-define=ORACLE_API_BASE_URL=http://192.168.40.50:8000` | 開発機のLANアドレス。テスターの端末からは到達できない |

### 4.3 サーバーとの差（4項目のみ）

バックエンドのインターフェース28メソッドのうち、アプリ単体で使えないのは4つだけ。

| 機能 | 理由 |
|---|---|
| 引継ぎコードの発行・利用 | 端末間でアカウントを付け替えるため、両端末が見る場所が要る |
| 通知トークン登録 | プッシュ基盤が要る |
| ~~問い合わせ~~ | **本作業で解消**（メーラーに委ねた） |

占いフロー・カード・テーマ・履歴・購入・外部リンク・お知らせ・分析は
すべてアプリ内で動く。文章はサーバー版と一字一句同じ（パリティテストで固定）。

## 8. 3大リスクの最終サマリー

### 利用者への影響

1. メールアプリが無い端末 → 宛先を文字で表示し、黙って失敗させない（テスト実装済）
2. 記入例の消し忘れ送信 → プレースホルダなので本文に残らない
3. 版数の取り違え → `pubspec.yaml` との一致をテストで機械照合

### システム

1. 鍵の紛失 → 上書き更新不可。バックアップとREADME・指紋を用意（オフサイトは未了）
2. 鍵の無い環境でのビルド失敗 → debug 署名へ落として通す。ただし配布は鍵必須と明記
3. 死にコードの残存 → `submitInquiry` を4ファイルから完全削除（`grep` で0件を確認）

### 運用

1. **グループ宛の誤配布** → 手順書 §2 で「個別指定」を明文化。実際に別アプリのテスターが混在していた
2. 開発用フラグ付きの誤配布 → 手順書 §3.1 とチェックリストに明記
3. リリースノートの改行でアップロード失敗 → `--release-notes-file` を使うと手順書に明記（実際に1度失敗した）
