# 作業1-3 カード番号の解釈 — 調査と方針

作成日: 2026-09-11
決定済み: ①表示はマスタの No. に合わせる ②番号に意味を持たせ、対応表をマスタに作る
未決: ③どう使うか（本書で提案）

## 1. WEB調査の結果

### 1.1 オラクルカードの番号は「通し番号」が既定

調べた範囲では、**オラクルデッキに標準の数秘体系は無い**という説明が一致していた。

- タロットが持つような固定の枚数・組（スート）・数秘の体系を、オラクルデッキは持たない。
- オラクルの番号は**ガイドブックを引くための通し番号**であることが多い。
- 枚数もデッキごとに異なり（36〜64枚程度が多い）、**意味づけは制作者が決める**。

∴ オーナーのご認識「オラクルカード占いは自由解釈が基本」は**調査でも裏づけられた**。
言い換えると、**番号に意味を持たせるかどうかは、こちらが決めてよい**。

### 1.2 タロットの「期日の読み」には確立した手順がある

一方、タロットで番号を期日に読む方法は定型化されている。

| 要素 | 役割 |
|---|---|
| **スート（組）** | **時間の単位**を決める。ワンド=日〜週／カップ=週〜月／ソード=日〜月／ペンタクル=月〜年 |
| **数字** | **数量**を決める。カップの4なら「4か月」、ワンドの8なら「8日」 |
| 大アルカナ | 期間を特定しない。人生の段階として読む |

さらに、**2つの方法を突き合わせると信頼性が上がる**とされる
（スートの偏りが示す季節と、数字の合計が示す数を照合する）。

### 1.3 本デッキに当てはめると

**本デッキは「単位」に相当するものを既に持っている。エレメントである。**

| エレメント | 枚数 |
|---|---|
| 地 | 12 |
| 火 | 11 |
| 水 | 11 |
| 風 | 7 |
| エーテル | 3 |

番号は 1〜44 で全カードに付いている。
∴ **スート＝エレメント、数字＝番号**と置けば、タロットの確立した手順をそのまま移せる。
新しい体系を発明する必要がない。

## 2. 方針

### 2.1 エレメント → 時間の単位、番号 → 数量

| エレメント | 単位 | 根拠 |
|---|---|---|
| 火 | **日** | 最も速い。タロットのワンドに対応 |
| 風 | **週** | 次に速い。ソードに対応 |
| 水 | **月** | 情の熟成。カップに対応 |
| 地 | **年** | 最も遅い。ペンタクルに対応 |
| エーテル | **定めない** | 根源・始原の3柱。大アルカナと同じ扱いで期日を特定しない |

番号はそのまま数量に使う（決定③「番号をそのまま使う」）。

> 例: 火のカードで No.6 → 「およそ6日のうちに」
> 　　水のカードで No.11 → 「およそ11か月のうちに」
> 　　エーテルのカード → 期日は示さず「時が満ちるとき」とする

**44 は大きすぎるのでは、という懸念について。** 地（年）で No.40 なら「40年」になる。
∴ **単位ごとに上限を設け、超える場合は幅で述べる**（§2.3）。

### 2.2 いつ出すか — 問われたときだけ

調査のとおりオラクルは自由解釈が基本で、**常に数字を語るのは本デッキの性格に合わない**。
既存の `質問タイプ分類`（19種・判定用キーワードつき）を使い、
**相談内容が期日・数量を問うているときだけ**出す。

| 相談内容 | 出す／出さない |
|---|---|
| 「いつ」「どのくらいで」「時期」「期限」 | **時期の読みを出す** |
| 「何人」「いくつ」「どれだけ」 | **数量の読みを出す** |
| それ以外（気持ち・進退・相性など） | **出さない** |

判定用のキーワードは `質問タイプ分類` と同じ作法で**マスタへ持つ**（コードに直書きしない）。

> **本日の託宣は相談内容を持たない**ため、原則として出さない。
> ただし番号そのものは常に表示する（決定①）。

### 2.3 マスタに作る対応表（決定②）

新シート **`番号解釈マスタ`** を作る。オーナーのDB更新と衝突しないよう、
既存シートには手を触れない。

| 列 | 内容 | 例 |
|---|---|---|
| エレメント | 火／風／水／地／エーテル | 火 |
| 単位 | 日／週／月／年／なし | 日 |
| 上限 | これを超えたら幅で述べる | 30 |
| 定型文 | `{n}` と `{unit}` を差し込む | およそ{n}{unit}のうちに動きがあります |
| 超過時の定型文 | 上限超えのときの言い方 | しばらく先になりますが、確かに巡ってきます |
| 数量の定型文 | 数量を問われたときの言い方 | 数にすれば{n}ほどが目安です |

**文面はマスタが持つ**ので、言い回しの調整にコード変更が要らない。

### 2.4 複数枚のときの照合（調査1.2の「2つの方法の突き合わせ」）

複数枚では次の順で決める。

1. **エレメントの最頻**で単位を決める（例: 5枚中3枚が火 → 日）
2. **番号は、そのポジションの主役**（1枚目＝起点、または位置の意味が「未来」のカード）を使う
3. 最頻が割れたら（同数）**より遅い単位**を採る（外して落胆させるより、遅めに言う）

**新しいAPIも新しい画面も作らない。** 既存の託宣文に段落が1つ増えるだけ。

### 3.1 番号の表示（決定①）

マスタの No. を表示する。図柄に描かれた番号とは現在ずれているが、
**オーナーがDBマスタを更新して揃える**とのことなので、アプリ側はマスタに従う。

> 揃うまでの間は、図柄の番号と表示の番号が食い違って見える。
> 更新が済むまで**表示を伏せておく**選択肢もある（承認事項イ）。

## 4. リスク

### 4.1 占いとしての妥当性

1. **外れたときの信頼低下** — 期日は最も外れが目立つ。→ 「およそ」「目安」と幅を持たせ、断定しない。禁止表現マスタの「必ず」「絶対」は既に機械で弾いている
2. **神格と無関係な数字の押しつけ** — 常時表示だと「角杙神は13だから…」という無関係な読みになる。→ **問われたときだけ**出す（§2.2）
3. **年単位の非現実的な数字** — 地の No.40 で「40年」。→ 単位ごとの上限と、超過時の言い回しをマスタに持つ

### 4.2 システム

1. マスタ未整備でも落ちない → 対応表が無ければ段落を出さない（fail-soft。既存の全マスタと同じ作法）
2. オフラインとの食い違い → 文章合成は内蔵エンジンに閉じており、Dart側へも同じ素材が同梱される。**パリティテストで固定**する
3. 判定キーワードの取りこぼし → 出ないだけで壊れない。語はマスタで足せる

### 4.3 運用

1. 図柄とマスタの番号の不一致 → オーナーの更新待ち。揃うまでの表示可否を承認事項イで確認
2. 文面の調整 → マスタの定型文を直すだけ。アプリ更新は不要
3. 多言語 → 定型文は当面**日本語のみ**（組み合わせ解釈と同じ扱い）。en/zh では段落を出さない

## 5. 承認をお願いする事項

| # | 事項 | 推奨 |
|---|---|---|
| ア | エレメント→単位の割り当て（火=日／風=週／水=月／地=年／エーテル=なし） | 案のとおり（タロットの確立した対応をそのまま移す） |
| イ | 番号の表示開始時期 | **DBマスタの更新が済んでから**表示する（図柄との食い違いを利用者に見せない） |
| ウ | 出す条件 | **期日・数量を問われたときだけ**（常時は出さない） |
| エ | 単位ごとの上限 | 日=30／週=12／月=18／年=10（超えたら幅で述べる） |
| オ | 複数枚のときの単位 | エレメントの最頻。同数なら遅いほうを採る |

> 上記の承認をもって作業4（実装）へ進みます。
> `番号解釈マスタ` の追加はスクリプトで行うため、**オーナーのxlsx編集は不要**です。
