## 4. 作業3: 修正方針

### 4.1 ①「占う」直後の分岐（新画面 U-R0）

```text
ホーム「占う」オーブ
 └ U-R0 種別選択（新規・2択の大ボタン）
    ├ 本日の託宣（ワンオラクル）
    │   └ デッキ選択 → シャッフル → 山選択 → カード確定 → 結果（現行フロー踏襲）
    └ リーディング（本格）
        └ U-R1 残数・権限の確認（**開始前に提示**）
            └ デッキ選択 → U-R2 スプレッド選択（3/5/7/フリー）
               → U-R3 テーマ（プルダウン）＋相談内容入力
               → シャッフル → 山選択 → カード確定×N → 結果（統合）
```

- **U-R1で先に提示する**（B6の是正）: 現在のプラン名・チケット残数・このスプレッドの必要枚数・実行後の残数。不足時は**その場で購入導線**（`/paywall`）。
  業界標準でも「消費前にコストと残高を明示」が定石（§5）。
- 「本日の託宣」は**1日1回無料**を維持（既存の `freeDailyLimit` 判定を流用。新パラメータを作らない）。
- 画面IDは `07_UI画面遷移_ワイヤーフレーム仕様書.md` の採番規則に合わせて **U-11/U-12/U-13** を新規採番（採番は承認後に確定）。

### 4.2 ②テーマ選択（プルダウン）＋相談内容の入力（U-R3）

- テーマは現行の6種を**プルダウン（DropdownButtonFormField）**へ変更。既存 `theme_selection_screen.dart` を**置換ではなく縮約**（グリッドは「本日の託宣」では不要になるため、リーディング側のみプルダウン）。
- 相談内容は**自由記述（複数行・最大200字目安）**＋「例: 転職すべきか迷っています」のヒント表示。**任意入力**とし、未入力でも従来どおり成立させる（fail-soft）。
- API拡張: `start_session` に `question_text: str | None` と `spread_id: str` を追加。`draw_count` は `spread_id` から導出し**二重管理しない**（パラメータ乱立防止）。
- 相談内容は**セッションに保持し、履歴にも保存**（振り返り価値が高い）。**外部送信はしない**（§4.4のB案採用時）。

### 4.3 ③結果文の自然化（3層）

**方針の骨子**: 「テンプレの穴埋め」から「**素材→構成→文体**の3層生成」へ。文章の組み立ては `InterpretationEngine` に閉じる。

| 層 | 内容 | 素材 |
|---|---|---|
| 素材層 | カードの基本的意味・テーマ別解釈・肯定/否定/中立/行動の4系キーワード・組み合わせルール | 44柱.xlsx／AI解釈用キーワード辞書／組み合わせ解釈ルール |
| 構成層 | 質問文→**質問タイプ分類でジャンル・状況・トーンを判定**（C3の是正）。スプレッドの**位置の意味**で各カードの役割を決め、導入→各位置→統合→行動提案の順に段落を組む | 質問タイプ分類／文脈パターンDB／**[新]スプレッド・ポジション定義** |
| 文体層 | 感情トーン設定の語尾・禁止表現を適用し、**接続表現マスタ**で段落を接続。体言止めを文章体へ整える | 感情トーン設定／**[新]接続表現マスタ** |

**生成方式の選択（承認事項A）**:

- **B案（推奨・既定）**: 上記3層を**内蔵エンジンで**実装。オフライン動作・費用0・審査容易・相談内容を外部へ出さない。既存の `compose_ja` を拡張し、`compose_combination`（latent）を**本配線**する。
- **C案（推奨・上位）**: B案を既定にしつつ、**「ディープリーディング」＝有料**のときだけサーバー経由でLLMを呼び、B案の生成物を**下書き**として推敲させる。既に存在する導線ボタンに実体を与えられる。相談内容の外部送信となるため**プライバシーポリシー改定と同意取得が必要**。
- A案（全面LLM）は**非推奨**: オフライン動作という既存資産を失い、1リーディングごとに費用とレイテンシが乗る。

### 4.4 ④シャッフル案内文の上部移動

- `shuffle_screen.dart` の `Column` の要素順を入れ替え、案内ブロック（デッキ/テーマ・進捗バー・案内文）を**カード表示域の上**へ移動。
- 併せて案内文は `SafeArea` 直下に固定し、**指の可動域（画面下半分）から外す**。実装は要素順の入替のみで、ロジック変更なし。

### 4.5 DB構成の改善（マスタ側）

| # | 改善 | 理由 |
|---|---|---|
| D1 | **`スプレッド定義`シート新設**（spread_id／名称／枚数／用途／必要チケット／対象プラン） | 枚数と課金をコードから追い出す。4.1のU-R2の供給元 |
| D2 | **`ポジション定義`シート新設**（spread_id／位置No／位置名／位置の意味／文中での役割） | 多枚リーディングの解釈を作る唯一の材料。現在**存在しない** |

## 5. 業界標準との照合（今回の追加Web調査）

- AIタロットの標準的なスプレッド構成は **1枚（単純な問い）／3枚（過去・現在・未来）／ケルト十字（複雑な状況）／カスタム**。**枚数は「質問の複雑さ」に対応させる**のが定石。
- AI生成の入力は **①カード ②位置 ③質問 ④文脈（履歴）** の4点セット。**位置の意味がカードの意味を変える**という前提が共通。
  → 本アプリは②③④のすべてが欠落（B1・D2・履歴未活用）。
- 結果表示は **ビジュアル配置 → 位置ごとの解釈 → 統合した物語** の順が標準。
- 質問文は「〜すべきか」より**現在形で具体的に**書かせるとリーディング品質が上がるとされ、**入力欄に例示を置く**のが一般的。
- 課金は**消費前に残高とコストを明示**するのが定石（本アプリは開始後に例外で弾く＝B6）。

## 7. リスク

### 7.1 UX・体験

1. 分岐画面の追加でホームからの手数が1段増える（→「本日の託宣」を上・大きく置き、既定動線の体感を落とさない）。
2. 相談内容の入力を必須にすると離脱が増える（→**任意入力**とし、未入力でも成立させる）。
3. 7枚・フリーは1画面に収まらず、選択と結果の一覧性が落ちる（→横スクロール＋位置ラベルで対応）。

### 7.2 システム

1. `ReadingResult` の複数枚化は**履歴・管理画面・分析に波及**（既存単数フィールドを残し、段階移行）。
2. オフライン実装（`offline_backend.dart`）の同時改修を怠ると、オフライン時だけ新フローが壊れる。
3. スプレッド定義をDB化すると、アプリ同梱マスタとサーバーの版ずれが起きうる（→既存の `export_master_assets.py` 経由に統一）。

### 7.3 運用・法務

1. C案（LLM）採用時は**相談内容が外部送信**される＝プライバシーポリシー改定・同意取得・審査対応が必要。
2. 文章生成の高度化に伴い、断定的な表現（診断・治療・投資助言）を避けるガードが必要（`感情トーン設定` の「避けるべき表現」を**機械的に検査**する）。
3. マスタの母数確定（D7）を先送りすると、以後の作業が44と66の両にらみになり手戻りが増える。
