# 不足機能 実装計画（是正対応案）

## 1. スコープ再定義

### 1.1 現在の位置づけ

- 現在成果物は「バックエンドMVP段階」と定義する。
- 仕様書フルスコープ（モバイル + 管理画面 + 運用基盤）ではない。

### 1.2 目標スコープ

- モバイルアプリ（U-01〜U-19）
- 管理画面（A-01〜A-08）
- バックエンドAPI本実装
- 永続DB + キャッシュ
- 通知運用
- 正式課金運用
- 分析基盤
- 外部導線

## 2. 実装フェーズ案

## Phase 0: 仕様トレーサビリティ固定（最優先）

実施項目:

- 章番号ベースの対応表を確定
- 画面IDごとの実装/未実装一覧を確定
- API実装一覧と未実装一覧を確定

完了条件:

- 仕様変更のない限り、差分更新だけで追跡可能な状態になること

## Phase 1: バックエンド本番化

実施項目:

- PostgreSQL + Redis へ移行
- ORMモデルとマイグレーション導入
- 認証拡張（/auth/apple, /auth/google, セッション管理）
- 課金強化（復元、失効、猶予、検証エラー処理）
- 通知配信ジョブ基盤（予約、セグメント）
- 監査ログと運用ログの整備

完了条件:

- インメモリ依存が排除され、再起動後もデータ整合が保たれること

## Phase 2: 管理画面実装（A-01〜A-08）

実施項目:

- 管理画面フロントエンド実装（Next.js想定）
- 管理者認証とロール制御
- カード/デッキ/テーマ/お知らせ/通知/ユーザー/問合せ管理
- KPIダッシュボード初版

完了条件:

- 非エンジニア運用で主要マスタ更新と告知運用が可能

## Phase 3: モバイルUI実装（U-01〜U-19）

実施項目:

- Flutterで画面実装
- U-05〜U-10 占い導線のUI統合
- U-13/U-14/U-15/U-16 外部導線の実装
- U-17/U-18 会員・課金・通知設定の実装

完了条件:

- 追補仕様書の画面項目を主要導線で満たすこと

## Phase 4: 分析・運用強化

実施項目:

- KPIイベント計測を主要導線に実装
- 通知効果測定、課金転換測定を実装
- 受入試験マトリクスに基づく総合テスト

完了条件:

- KPIの継続取得と運用改善サイクルが成立すること

## 3. 優先度と依存関係

| 優先度 | 項目 | 依存 |
|---|---|---|
| P0 | 仕様トレーサビリティ固定 | なし |
| P1 | DB/認証/課金本番化 | P0 |
| P1 | 管理画面基盤 | P0 |
| P2 | モバイルUI主要導線 | P1 |
| P2 | 通知運用高度化 | P1 |
| P3 | 分析高度化とAB運用 | P2 |

## 4. 受入判定基準（抜粋）

- 仕様章番号ごとの対応表が更新済みであること
- 画面ID単位で実装済み/未実装が提示されること
- API未実装一覧が明示されること
- DB設計と実装モデルの対応が追跡できること
- テスト観点マトリクスで未カバーが明示されること
