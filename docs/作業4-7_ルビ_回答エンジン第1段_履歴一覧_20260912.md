## 2. ① 神名のルビ

### 2.1 直したところ

ルビ（`reading`）は44柱すべてマスタにあり、札の絵と見出しには出ていたが、
**エンジンが組み立てる本文に入っていなかった**。

| 箇所 | 変更 |
|---|---|
| `{神名}` の差し込み | `_with_ruby(card)` を通す |
| 位置別の段落（【過去】など） | 同上 |
| 組み合わせ解釈 | `name_ja` 直結をやめ `_with_ruby` へ |

ルビが空のカードは括弧を出さない（fail-soft）。

### 2.2 多言語

本文（`compose_reading`）は**日本語専用**で、en/zh はカードマスタの訳文をそのまま使う
（`reading_service.py` L264-269）。∴ 多言語への影響は無い。

### 2.3 承認イについて — 対応が要らなかった

方針書では「読み上げはルビを読まない」としたが、実装を確認したところ
**本アプリに読み上げ（TTS）は無い**。画面上部のスピーカーは
`SoundService` の**効果音ON/OFF**トグルである（`speaker_toggle.dart`）。

∴ ルビ抜きの文を別に持つ必要は無く、**何も作っていない**。
将来TTSを入れる場合はここで分岐が要る、という申し送りだけ残す。

## 3. ② 回答エンジン 第1段

### 3.1 羅列の解消

原因は `_as_phrase`（L237-240）が**マスタの列挙を無編集で流していた**こと。

```text
theme_meanings.money = "大胆な改革。破壊的イノベーション。古いシステムを壊して新しい方法へ。"
                     ↓ _as_phrase
"大胆な改革、破壊的イノベーション、古いシステムを壊して新しい方法へ"  ← 3つ全部
```

意味は3〜5文の列挙で、全264通り（44柱×6テーマ）がこの形だった。

**`_pick_meaning()` を新設し、1つだけ選ぶ**ようにした。
選び方はカードIDと位置名の md5 で、同じ引きなら何度でも同じ文になる。
位置ごとに違う番号が当たるため、**3枚引きなら全体では複数の意味が読み手に届く**。

### 3.2 結論を先に置く

従来は「導入 → 各カード → 組み合わせ → 助言 → 締め」と**並べるだけ**で、
問いの中身を一度も使っていなかった（使うのは分類だけだった）。

**`問いの型マスタ`（新規・7行）** を追加し、導入の直後に結論を1文置く。

| 区分 | 判定語の例 | 結論文 |
|---|---|---|
| 可否 | できます／可能／叶う | {主題}について、いま示されているのは「{意味}」という流れです。 |
| 時期 | いつ／時期／タイミング | {主題}の時期については、「{意味}」という流れの中にあります。 |
| 方法 | どうすれば／方法／コツ | {主題}をどう進めるかについて、鍵になるのは「{意味}」です。 |
| 選択 | どちら／すべきか／迷って | {主題}の選択について、カードが照らしているのは「{意味}」です。 |
| 気持ち | 気持ち／本音／どう思 | {主題}をめぐる心の動きは、「{意味}」として現れています。 |
| 原因 | なぜ／理由／原因 | {主題}の背景にあるのは、「{意味}」という流れです。 |
| 既定 | （判定語なし） | {主題}について、いま見えているのは「{意味}」という流れです。 |

差し込みは `{主題}`（問いから取る）と `{意味}`（カードから取る）の2つだけである。

**型は当たった語の数で選ぶ。** 「いつごろ結婚できますか」は
可否1件より時期2件が勝ち、より具体的な型になる。

### 3.3 主題語の取り出し

**自由文の読解はしない。** 名詞らしい塊（漢字・カタカナ・英字の連なり）を全部拾い、
**最も長いもの**を主題とする。同じ長さなら先に出たほうを採る。

| 問い | 主題 |
|---|---|
| 宝くじのロト7で1等を当てたい | ロト7 |
| 転職すべきか迷っています | 転職 |
| 彼の気持ちが知りたい | 彼 |
| いつごろ結婚できますか | 結婚 |
| なぜ人間関係がうまくいかないのでしょうか | 人間関係 |

「気持ち」「どちら」等は**型の判定語であって主題ではない**ため外す。
取り出せなければ**結論文を出さない**（一般論を語るより、何も言わないほうが害が小さい）。

### 3.4 同じ文を二度言わない

結論は最後のカード（未来・結果の位置）から作るため、
そのまま【未来】の段落でも同じ意味が出てしまう。
∴ `_pick_meaning(..., avoid=...)` で**結論で使った番号を外す**。

### 3.5 実際の出力

```text
「宝くじのロト7で1等を当てたい」という問いに、いま整えるべきなのは、次の流れです。

ロト7について、いま見えているのは「組織に生命力」という流れです。      ← 結論（新）

【過去】綿津見神（ワタツミ）。ここへ至るまでの流れと背景には、
　　　　神秘的な商品・サービスが横たわっていたようです。              ← 意味1つ・ルビ

【現在】神産巣日神（カミムスビ）。あなたのまわりで、
　　　　チームを育成するが動き始めています。

【未来】気吹戸主（イブキドヌシ）。このまま進めば、
　　　　新鮮なアイデアを吹き込むへ向かう可能性が高いでしょう。         ← 結論と別の意味

続いて、綿津見神（ワタツミ）と気吹戸主（イブキドヌシ）は「流動化」の関係にあります。…

国津神/自然神である綿津見神（ワタツミ）は、海・深層のときを告げています。

あなたの直感が「息吹を入れる・新鮮さをもたらす」と囁くなら、その声に従ってみてください。
新鮮な風・生命力の注入へつながっていくでしょう。

小さな一歩から始めてください。
```

### 3.6 第1段の限界（正直に）

**問いの事情は汲めない。** 「前回外した」「家族に反対されている」といった文脈は
読めず、主題語1つと型1つに縮めている。これは第1段の設計上の限界であり、
**承認エ（生成AI）の判断材料**である。

## 4. ③ 履歴を一覧＋詳細へ

### 4.1 直したところ

```dart
// 変更前（history_screen.dart L74）
subtitle: Text('${item.createdAt}\n${item.fullText}'),  // 全文。3枚引きで800字超
```

| # | 変更 |
|---|---|
| 1 | `HistoryItem` に **`spread_id`** を追加（models／schemas／store／API／Dartモデル／オフライン） |
| 2 | 一覧は **種別の札＋`YYYY/M/D HH:MM`** の1行。全文は出さない |
| 3 | **詳細画面（U-22）を新設**。全文・種別・日時・削除を持つ |
| 4 | 削除を詳細へ移した（一覧のゴミ箱は押し間違えると取り返しがつかない） |

### 4.2 既存データ

`spread_id` を持たない履歴は **`daily`（託宣）** として扱う。
サーバー・オフライン・Dartモデルの3箇所すべてで既定値を置いた（欠損で画面が壊れない）。

Postgres には移行 **`002_history_spread_id`**（up/down）を追加し、
`DEFAULT 'daily'` 付きで列を足す。SQLAlchemy 側も `server_default` を置いたため、
新規構築（`create_all`）でも同じ形になる。

### 4.3 日時

ISO文字列（`2026-09-12T22:21:03.123456+09:00`）をそのまま出していたため、
端末のタイムゾーンで `YYYY/M/D HH:MM` に整形する。
解釈できない値はそのまま返す（fail-soft）。

## 8. 3大リスクの最終サマリー

### 占いとしての妥当性

1. ルビの繰り返しで読みにくい → 承認アに従い全出現。初出のみへ戻すのは `_with_ruby` の呼び分けだけで足りる
2. 意味を1つに絞って情報が減る → 位置ごとに違う番号が当たり、3枚引きなら複数が届くことをテストで固定
3. 主題語の取り違え → 取れなければ結論を出さない。誤った主題で語るより黙る

### システム

1. パリティの崩れ → ルビ・結論を両実装へ移植し、期待値7ケースで一字一句を固定
2. 履歴に列を足した → サーバー・オフライン・Dartの3箇所に既定値。既存データは託宣扱い
3. Postgres の既存環境 → 移行 002（`IF NOT EXISTS` ＋ `DEFAULT 'daily'`）と `server_default` の両方を用意

### 運用

1. 文面の調整 → 結論文・語り口はすべてマスタ。アプリ更新は不要
2. 判定語の追加 → `問いの型マスタ` に行を足すだけ
3. 履歴の詳細画面が増えた → 画面ID表の更新が未了（§7-5）
