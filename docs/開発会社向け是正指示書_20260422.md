## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書名 | 開発会社向け是正指示書 |
| 対象案件 | リーディングアプリ開発案件 |
| 作成日 | 2026-04-22 |
| 版数 | Ver.1.0 |
| 目的 | 開発会社に対し、現成果物の是正事項、優先順位、提出物、受入条件を正式通知するための文書 |

## 2. 指示の目的

本指示書は、現時点の成果物がバックエンドMVP相当には到達している一方で、
詳細仕様書および追補資料に対する全体準拠には至っていないことを踏まえ、
是正対象、実施順序、提出義務、受入条件を明確化するために発行する。

現状は、バックエンドAPIの一部拡張、モバイル層および管理画面層の骨格追加までは確認できるが、
本番用認証保護、詳細UI、状態管理、E2E試験、DB永続化、通知運用、分析運用は未完了である。

## 3. 現状評価

現成果物は、占いフローAPI、履歴保存、無料制限、有料制限などの基本機能については
一定の実装が確認できるため、バックエンドMVPとしては有効である。

一方で、モバイルアプリ本体、管理画面、PostgreSQL/Redisを前提とした永続化、
通知配信運用、分析基盤、外部導線の各領域は未実装または部分実装に留まっており、
仕様全体に対する受入は不可と判断する。

## 4. 是正対象の基本方針

是正は、単発修正ではなく、仕様トレーサビリティ、基盤本番化、管理画面、
モバイルUI、分析運用の順に段階実施することを原則とする。

ただし、今回の即時指示対象としては、運用リスクと後続工程への依存関係を踏まえ、
`admin_app` の依存更新、`mobile_app` の状態管理および実APIバインド本実装、
ならびに PostgreSQL/Redis への移行着手を優先是正事項とする。

## 5. 是正指示事項

### 5.1 指示事項1: admin_app 依存更新と npm audit 対応

`admin_app` は新規作成済みであるが、現状は管理画面骨格段階であり、
本実装に着手する前提として依存ライブラリの安全化を完了させる必要がある。

開発会社は、`admin_app` の依存ライブラリを安全版へ更新し、`npm audit` 対応を反映すること。
high および critical 脆弱性は 0 件を完了条件とする。

実施内容:

- `package.json` および `package-lock.json` の更新
- 脆弱性影響調査の実施
- 互換性確認の実施
- ビルド確認、lint確認、主要画面遷移確認の実施

提出物:

- 更新後ソース一式
- 依存更新一覧
- `npm audit` 実行結果
- ビルド結果
- 互換性影響報告書

完了条件:

- high / critical 脆弱性が 0 件であること
- 更新後ビルドが成功すること
- 管理画面骨格の主要遷移に破壊影響がないこと

### 5.2 指示事項2: mobile_app の状態管理と実APIバインド本実装

`mobile_app` はディレクトリ、ルーティング、APIクライアント、各画面骨格が追加されているが、
本番用の状態管理、詳細UI、E2E試験は未実装である。

また、仕様対実装対応表では、U-04以降の多くがAPIのみの部分実装、
またはUI未実装として整理されているため、モック前提の接続ではなく、
実APIに接続した本実装へ移行させる必要がある。

対象範囲:

- U-03 ホーム
- U-04 デッキ選択
- U-05 テーマ選択
- U-06 シャッフル
- U-07 山選択
- U-08 カード展開
- U-09 結果表示
- U-10 履歴一覧
- U-13 お知らせ
- U-17 マイページ
- U-18 課金画面
- U-19 問い合わせ

実施内容:

- 状態管理方式の固定と全体適用
- 認証、テーマ、占いセッション、履歴、課金、通知設定の一貫管理
- モック通信の廃止と実API接続への全面置換
- ローディング、エラー表示、再試行、未ログイン時制御の実装
- 主要導線の画面遷移確認

提出物:

- 状態管理設計説明書
- 画面別API接続一覧
- 実機またはエミュレータでの操作録画
- エラー系を含む試験結果
- 未完了項目一覧

完了条件:

- 主要導線でアプリ単体デモが成立すること
- 実APIから取得したデータで U-03〜U-10 の遷移が完了すること
- U-13、U-17、U-18、U-19 も実API連携で動作すること

### 5.3 指示事項3: PostgreSQL/Redis 移行とバックエンド永続化着手

詳細仕様書では、システム構成として PostgreSQL および Redis を前提とした構成が明示されているが、
現状は `InMemoryStore` 依存であり、再起動後の整合性を保証できない。

不足機能実装計画でも、PostgreSQL + Redis への移行、ORM導入、マイグレーション導入、
認証拡張、課金強化、通知配信ジョブ基盤は Phase 1 の中心項目として整理されている。

優先対象モデル:

- users
- decks
- cards
- themes
- reading_sessions
- reading_results
- history_items
- subscriptions
- ticket_wallets
- announcements
- inquiries

実施内容:

- `InMemoryStore` 依存箇所の洗い出し
- ORM モデル設計
- マイグレーション導入
- 初期データ投入方式の確立
- Redis の用途定義（セッション、キャッシュ、通知ジョブ等）
- 再起動後整合性試験

提出物:

- DB論理設計書
- ORMモデル一覧
- マイグレーションファイル一式
- 初期データ投入手順書
- Redis 利用方針書
- 永続化試験結果

完了条件:

- サーバ再起動後も履歴、課金状態、お知らせが保持されること
- 永続DBから主要APIが正常応答すること
- インメモリ依存が主要導線から排除されること

## 6. 実施順序

是正は以下の順序で進めること。

1. `admin_app` 依存更新と npm audit 対応
2. PostgreSQL/Redis 移行設計と永続化着手
3. `mobile_app` 状態管理と実APIバインド本実装
4. 認証、課金、通知、分析の本番運用強化

この順序は、セキュリティ、基盤整合性、UI本実装の依存関係を踏まえたものであり、
順序変更は事前承認がない限り認めない。

## 7. 受入条件

開発会社は、各是正事項について、ソースコード提出のみではなく、
実行確認ベースの証跡を必ず提出すること。

### 7.1 共通受入条件

- 仕様章番号ごとの対応表が更新済みであること
- 画面ID単位で実装済み/未実装が提示されること
- API未実装一覧が明示されること
- DB設計と実装モデルの対応が追跡できること
- テスト観点マトリクスで未カバーが明示されること

### 7.2 個別受入条件

| 項目 | 受入条件 | 検証方法 |
|---|---|---|
| admin_app 依存更新 | npm audit high / critical = 0 | 実行ログ提出 |
| mobile_app API本実装 | 主要画面遷移が実APIで完了 | 操作録画 + 接続ログ |
| DB永続化 | 再起動後も主要データ保持 | DB参照 + API再取得 |

## 8. 提出期限と提出形式

初回再提出では、少なくとも次の資料を一式提出すること。

- 是正実施報告書
- 更新済み仕様トレーサビリティ表
- 画面ID対応表
- API対応表
- DB設計関連資料
- テスト結果一式
- 未完了事項一覧
- 次ラウンド実施計画

提出形式は、Markdown または PDF を正本とし、
ソースコード差分、ログ、録画、補足資料を別添とする。

## 9. 判定

現時点の判定は「受入不可」とする。

理由:

- 現成果物がバックエンドMVP相当には達しているものの、
  仕様全体に対する不足が大きい。
- 特にモバイルUI、管理画面、永続DB、通知運用、分析運用が未充足。
