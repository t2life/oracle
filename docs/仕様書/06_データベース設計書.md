## 2. 永続化バックエンドの選定方式

本システムは単一のDB技術に固定せず、環境変数で3段階を切り替える設計になっている（`orchestrator._build_store`、`06_詳細設計書_バックエンドAPI.md`§6参照）。

| `ORACLE_PERSISTENCE_BACKEND` | 実体 | 用途 |
|---|---|---|
| `inmemory`（既定） | `InMemoryStore` | ローカル開発・テスト。プロセス再起動でデータ消失 |
| `postgres` / `postgresql` | `HybridStore`（Postgresのみ有効） | 永続化重視、キャッシュ無し |
| `redis` | `HybridStore`（Redisのみ有効） | キャッシュ重視（永続化なし、揮発） |
| `hybrid` | `HybridStore`（Postgres+Redis） | 本番相当の想定構成 |

`ORACLE_RUNTIME_MODE=staging`または`production`の場合、`inmemory`指定は起動時に`RuntimeError`で拒否される（誤ってテスト構成のまま本番相当環境を起動することを防ぐガード）。

## 3. PostgreSQLスキーマ（scripts/migrations/001_expand_persistence_up.sql）

| テーブル | 主キー | 主な列 | インデックス |
|---|---|---|---|
| `users` | user_id | plan, tickets, subscription_expires_at, created_at, updated_at, visit_count | — |
| `subscriptions` | user_id | plan_id, status, expires_at, updated_at | — |
| `ticket_wallets` | user_id | balance, updated_at | — |
| `announcements` | announcement_id | title, body, category, start_at, end_at, is_important, link_url | `idx_announcements_start_at` |
| `inquiries` | inquiry_id | user_id, category, body, email, created_at | `idx_inquiries_user_id`, `idx_inquiries_created_at` |
| `audit_logs` | audit_id | actor_type, actor_id, action, resource_type, resource_id, detail_json, occurred_at | `idx_audit_logs_occurred_at` |
| `reading_results` | session_id | user_id, theme_id, deck_id, card_id, card_name, keywords_json, interpretation_text, caution_text, created_at, copied | `idx_reading_results_user_id` |
| `reading_history` | history_id | user_id, session_id, created_at, theme_id, deck_id, card_id, summary, full_text, plan_at_creation | `idx_reading_history_user_id`, `idx_reading_history_created_at` |

ダウンマイグレーション（`001_expand_persistence_down.sql`）は上記全テーブルのDROPのみで構成される。マイグレーション適用/ロールバックは`scripts/run_migration.py up|down`で実行し、DB未起動時は`connect_timeout=5`でハングを回避する設計。

### 3.1 未テーブル化のモデル（要今後対応）

`models.py`で定義済みだが、上記マイグレーションにテーブルが無いもの:

- `Profile`（display_name, locale）
- `AuthAccount`（provider, provider_user_id, email）
- `Theme` / `Deck` / `Card`（コンテンツマスタ。現状はコード内`AppConfig`シードのみでInMemory管理）
- `Product` / `ExternalLink` / `LiveEvent`（同上）
- `PushCampaign` / `NotificationSetting`
- `AdminRole` / `AdminUser` / `AdminSession`
- `AnalyticsEvent`

これらはPostgreSQL移行が未着手のため、`ORACLE_RUNTIME_MODE=staging/production`かつ`hybrid`稼働時でも、これらのドメインは引き続きInMemory（プロセス揮発）で保持される。詳細は`11_今後の開発ロードマップ.md`のPhase 1残課題を参照。

## 4. HybridStoreの読み書きパターン

`HybridStore`（`InMemoryStore`を継承）は以下のドメインについてのみPostgres/Redis連携を実装済み:

| ドメイン | 書込 | 読込優先順 |
|---|---|---|
| ユーザー（users） | InMemory→Postgres upsert | InMemory→（無ければPostgres fetch） |
| 占い結果（reading_results） | InMemory→Postgres upsert＋Redis set（TTL 1800秒） | Redis→InMemory→Postgres |
| 履歴（reading_history） | InMemory→Postgres insert＋Redisキャッシュ削除（invalidate） | Redis（TTL 120秒）→InMemory→Postgres |
| お知らせ（announcements） | InMemory→Postgres upsert＋Redisキャッシュ削除 | Redis（TTL 120秒）→InMemory→Postgres |
| 問合せ（inquiries） | InMemory→Postgres insert＋Redisキャッシュ削除 | Redis（TTL 120秒）→InMemory→Postgres |
| 監査ログ（audit_logs） | InMemory→Postgres insert | InMemory優先、空ならPostgres |

各操作はPostgres/Redis呼び出し例外を握りつぶし、InMemory側の結果を返す「ベストエフォート」方針（段階導入中の可用性優先）。

## 5. Redisキー設計

| キー形式 | 用途 | TTL |
|---|---|---|
| `oracle:reading_result:{session_id}` | 占い結果キャッシュ | 1800秒 |
| `oracle:history:{user_id}` | 履歴一覧キャッシュ | 120秒 |
| `oracle:announcements:active` / `oracle:announcements:all` | お知らせキャッシュ（公開中／全件） | 120秒 |
| `oracle:inquiries:all` | 問合せ一覧キャッシュ | 120秒 |

プレフィックスは`ORACLE_REDIS_PREFIX`（既定`oracle:`）で設定化。

## 7. 今後の対応（優先度順）

1. `subscriptions`/`ticket_wallets`テーブルへの実書込経路の実装（現状はマイグレーションでテーブルのみ存在し、`users`テーブルのカラムに統合済み。仕様上の分離モデルへ揃えるか、統合設計を正式採用するかの判断が必要）。
2. `themes`/`decks`/`cards`/`products`/`external_links`/`live_events`のマスタテーブル化（現状は全てコード内シード値のInMemory管理のため、管理画面からの恒久的なマスタ更新が本番運用では反映されない）。
3. `analytics_events`のPostgres化（現状InMemoryのため、プロセス再起動でKPI集計対象イベントが失われる）。
4. `admin_users`/`admin_roles`のPostgres化（管理者アカウントの永続化）。
