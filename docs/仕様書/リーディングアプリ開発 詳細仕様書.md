## 2. 目的

本書は、リーディングアプリ開発企画書を基に、開発会社が設計、見積、実装、試験、運用設計を進めるために必要なアプリ詳細仕様を整理したものである。企画書では、オリジナルオラクルカードを使用したリーディングアプリとして、30〜80代女性を主対象に、日本神話デッキを中核としつつ、ショップ送客、本格鑑定送客、VTuber配信導線を含む収益構造を構想している。[cite:174]

また、無料ユーザーは1日1回の1枚引き、有料ユーザーは複数テーマ、3枚引き、より深いリーディングを利用可能とする料金・体験差分が明示されているため、本仕様ではこの差分を中心に、会員、通知、課金、管理画面、分析、外部連携を含む全体仕様を定義する。[cite:174]

## 3. 背景と事業前提

本アプリは、単体の占いアプリではなく、VTuber活動、物販、オンライン鑑定、メール鑑定、ライブ配信と連携するエコシステムの中核チャネルとして位置づけられる。[cite:174] 企画書では「本物の霊能者が力を込めたオリジナルオラクルカード」「写実的・神秘的・幻想的な世界観」「可愛すぎない落ち着いたデザイン」を重視している。[cite:174]

市場面では、占星術・スピリチュアル・ウェルネス系アプリは、継続課金、都度課金、通知による再訪導線、パーソナライズ体験の組み合わせが収益性向上に有効とされている。[cite:175][cite:177][cite:181] そのため本アプリも、1回きりの占い体験ではなく、継続利用と送客を最大化する構造で設計する必要がある。[cite:175][cite:177]

## 5. プロダクトコンセプト

本アプリは、神託を「遊び」ではなく「意味あるメッセージ体験」として提供することを主眼とする。企画書では、1日1回占える宣託、テーマ選択、手で扱う感覚を重視したシャッフル、カード画像＋キーワード＋テーマ別解釈の提示が中核体験として定義されている。[cite:174]

また、結果画面にはメッセージの重みを持たせる文言を添える前提が示されており、UI文言、通知文言、課金導線文言、VTuber人格表現も含めて、ブランドトーンの統一が必須である。[cite:174]

## 9. ユーザー機能要件

### 9.1 オンボーディング

初回起動時に、アプリの世界観、利用上の注意、無料範囲、通知許諾、会員登録メリットを案内する。ターゲット年齢層が高めであるため、説明は簡潔・視認性重視とし、文字サイズ、コントラスト、UI密度を過剰に詰め込まない設計とする。[cite:174]

### 9.2 ホーム

ホーム画面は、以下の要素を表示する。

- 今日の宣託開始ボタン
- テーマ別占い導線

- お知らせバナー
- ショップ導線
- 本格鑑定導線
- ロンの部屋導線
- マイページ導線[cite:174]

### 9.3 デッキ選択

初期実装では以下を管理対象とする。

- 日本神話デッキ（メイン）
- 龍神デッキ
- ブライスドールデッキ[cite:174]

デッキごとに、カード一覧、カード画像、解釈文、販売可否、公開状態、並び順を管理可能とする。

### 9.4 テーマ選択

テーマ選択は、企画書に基づき以下を標準テーマとする。[cite:174]

- 恋愛
- 仕事
- お金
- 健康
- 人間関係
- 魂
- 覚醒
- カルマ
- 前世

テーマは運営側が追加・非表示・並び替え可能とする。

### 9.5 占い体験フロー

占い体験は以下の状態遷移で構成する。[cite:174]

1. テーマ選択
2. シャッフル開始
3. シャッフル終了判定
4. 3山分割表示
5. 山選択
6. 横一列展開
7. カード選択
8. カードオープン
9. 結果表示
10. コピー／保存／課金導線

### 9.6 シャッフル仕様

シャッフルは、ユーザーの指スワイプに連動してカード束が動く演出を行う。実装上は、抽選ロジックとアニメーションロジックを分離し、抽選結果はセッション開始時に確定、演出のみスワイプ入力で変動させる方式を推奨する。

シャッフル終了判定は、以下の条件を基本とする。

- 最終スワイプから1.0〜2.0秒操作がない
- 指が画面から離れている
- 最低操作量閾値を超えている

### 9.7 山選択仕様

シャッフル終了後、カード束は自動的に3山へ分割して表示する。[cite:174] ユーザーは任意の1山を選択し、選択山のみが次画面で展開される。

### 9.8 カード展開・選択仕様

選択山は、横一列で展開し、左右スクロール可能とする。[cite:174] ユーザーは任意のタイミングで1枚を選択し、ダブルタップまたは明示ボタンで確定する方式を採用する。

### 9.9 結果表示仕様

結果画面では以下を表示する。[cite:174]

- カード画像
- カード名
- キーワード
- 選択テーマに応じた解釈文
- 必要に応じた注意文
- コピー機能
- 履歴保存
- 次回利用案内
- 有料アップグレード導線

結果文言には、企画書に沿って、受け取ったメッセージを伝える形式の重みづけ表現を含める。[cite:174]

### 9.10 履歴仕様

無料ユーザーは直近3件のみ、有料ユーザーは無制限保存とする案が企画書に示されている。[cite:174] 履歴には、日時、テーマ、デッキ、カード、要約、全文、課金区分を保持する。

### 9.11 カード一覧

全64枚のカードを一覧表示し、カード名、基本的意味、カテゴリ、デッキ別分類を閲覧可能とする。[cite:174] 将来の66柱対応やデッキ拡張も見越し、カード枚数はマスタ管理とし固定値で実装しない。

## 11. 課金仕様

企画書では、無料、チケット、サブスクの三層モデルが提案されている。[cite:174] また、占いアプリ分野では、サブスクと都度課金の併用が高LTV化に有効とされている。[cite:177][cite:181]

### 11.1 無料プラン

- 1日1回「今日の宣託（1枚引き）」
- 履歴は直近3件のみ
- 一部テーマまたは深い解釈は制限[cite:174]

### 11.2 チケット課金

企画書案を標準初期値とする。[cite:174]

| 商品 | 価格案 | 内容 |
|---|---:|---|
| 初回お試し | 300円 | 30枚 |
| チケット20枚 | 500円 | 消費型 |
| チケット50枚 | 1,000円 | 消費型 |
| チケット120枚 | 2,000円 | 消費型 |

1セッションあたりの消費枚数は、占い種別に応じて1〜3枚で管理する。[cite:174]

### 11.3 サブスクリプション

企画書案では、月額500円、または7日間無料トライアル付きの月額プランが想定されている。[cite:174]

サブスク特典は以下を基本とする。

- 毎日1回「今日の宣託」利用可能
- 月内上限付きテーマ別スプレッド利用
- 履歴無制限
- サブスク限定占い（月1本）
- 3枚引き・複数引き解放[cite:174]

### 11.4 課金実装要件

- Apple In-App Purchase / Google Play Billing 利用
- サーバー側レシート検証
- 購入復元
- 解約・失効・猶予期間管理
- 無料トライアル判定
- 二重課金防止
- 権限状態の即時反映

## 19. システム構成図

```text
[ iOS App / Android App ]
        │
        ├─ 認証SDK
        ├─ Push通知SDK
        ├─ 課金SDK
        └─ 分析SDK
        │
        ▼
[ API Gateway / Backend ]
        ├─ Auth Service
        ├─ Reading Service
        ├─ Content Service
        ├─ Billing Verification Service
        ├─ Notification Service
        ├─ User / History Service
        ├─ External Link Service

              │
              ├─ PostgreSQL
              ├─ Redis
              ├─ Object Storage
              ├─ FCM / APNs
```

この構成は、占いロジック、会員、通知、課金、CMSを分離し、将来的なデッキ拡張や多言語展開に適した形である。[cite:174][cite:175]

## 20. アーキテクチャ方針

### 20.1 推奨構成

- フロントエンド: Flutter
- バックエンド: FastAPI または Node.js
- DB: PostgreSQL
- キャッシュ: Redis
- 管理画面: Next.js
- Push通知: FCM / APNs
- 分析: Firebase Analytics + BigQuery
- インフラ: AWS または GCP

### 20.2 方針

- モバイルアプリはクロスプラットフォームで保守効率を優先する
- 占い抽選ロジックと演出ロジックを分離する
- コンテンツは管理画面で更新可能にする
- 課金状態はクライアント依存にせずサーバー検証とする
- 分析イベントを全主要導線で取得する
